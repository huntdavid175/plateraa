# Storefront (`@brixx/storefront`)

The online store customers order from (plan.md §4.0): one link per business, `STOREFRONT_URL/<slug>`, that the vendor shares on WhatsApp and Instagram. Next.js 16 (App Router, Turbopack), React 19, Tailwind 4. Phone first; on a laptop the cart is a side panel.

## Design

- Built to the user's Figma Make design, `design/storefront design.make` (kept out of `public/`, which the site serves to anyone). It's a zip; its code is a git pack under `make_repos/` (unpack it as described for the dashboard's design). The screens are in `src/App.tsx`. Its sample data isn't used.
- Colours are CSS variables in `app/globals.css`, exposed as Tailwind names: `bg-page`, `bg-card`, `bg-tile`, `border-border`, `text-ink`, `text-muted`, `bg-brand`, `bg-brand-tint`, `text-green` / `bg-green-bg`, and so on.
- **The whole look is the owner's choice** (user request, 13 Sep), but **in daylight every store stands on white** (16 Sep, user request): each look's light palette is the same white page, white cards and neutral greys, and the owner's colour shows in the band across the top (`hero`) and in everything that acts — buttons, the round **+** on each item, the chosen row. Dark mode still takes the look's own dark shade throughout. `STOREFRONT_LOOKS` in `@brixx/shared` has eighteen looks since 19 Nov (user request: more, and Classic in black and white), in the picker's order: Classic (black and white), Sand (Classic's old warm peach and burnt orange), Espresso, Jollof, Mango, Shea, Kente, Citrus, Palm, Forest, Lagoon, Sky, Midnight, Plum, Berry, Hibiscus, Pepper and Harmattan. Classic, Espresso, Forest, Midnight and Berry carry a dark band with light words; the rest a pastel one. A look's key never changes once stores use it (the keys are saved; `orange` is Jollof). Each has a light and a dark set: the page colour the owner picks, `card`, `tile`, `border`, `ink`, `muted`, a stronger band across the top (`hero` / `on-hero`), and buttons in a colour that goes with the page (`brand`, `on-brand` for words on buttons, `brand-ink` for words in the button colour). `<Themed theme>` writes them onto the page's root (`:root:root` and `:root.dark`), and `globals.css` works out `--brand-hover` and `--brand-tint` from them. Use `text-on-brand` on `bg-brand`, `text-brand-ink` for button-coloured words, and never hard-code a colour. `storefront.test.ts` in `@brixx/shared` checks every look's contrast: run it after changing one. Keep `@theme inline` in `globals.css`: with plain `@theme`, `--color-brand` settles on :root's default orange and the owner's colour only reaches things that use `var(--brand)` directly (it happened on 13 Sep).
- Dark mode follows the phone, with a switch remembered in the browser (`brixx-dark`), applied before the first paint by the script in `app/layout.tsx`.
- DM Sans and DM Mono come from `@fontsource`, so builds need no network. Money is `ghs()` (`lib/money.ts`), from whole pesewas.
- **The Brixx logo** (15 Sep): `app/favicon.ico`, `app/icon.png` and `app/apple-icon.png` are the tab and home-screen icons, which Next serves by their names for every page, each store's included; `public/logo.png` is the mark on Brixx's own page (`app/page.tsx`), where the 🍲 used to be. `Message` takes a picture or an emoji as its `icon`. They're made by `pnpm brand:assets` from `public/images/brixx-logo.png` at the repo root, so don't edit them by hand. The store's own logo is a different thing: the owner uploads it (`logoUrl`, see Photos).

## How it works

- **Only the storefront's server talks to the API** (`lib/api.ts`; `BRIXX_API_URL`, the Render API by default). Pages load their data on the server, and the browser calls server actions (`app/actions.ts`) to place an order, pay and check a payment. Actions never throw: they return `{ ok: false, message }` for the page to show.
- `app/[slug]/page.tsx` reads the store fresh on every visit; `storefront.tsx` is the client side. Its screens are `store`, `info`, `order` and `paying`.
- **The order is one page** (`OrderScreen`, 16 Sep, user request): the cart and checkout used to be two screens and are now one, to the reference the user shared — the items with their photo and a − 1 + stepper, "Add more", a note for the kitchen, "Delivery or pickup?" with each zone's fee, where to deliver, who they are, how they'll pay, what it comes to, and one button at the foot ("Pay GH₵ x", or "Place order" for cash). Emptying it is the bin in the header. `PricedLine` carries `photoUrl` for the rows. **People also add** (`AlsoAdd`) is a sideways row of what sells most here, minus what's already in the order: the API sends `popular` (item ids, best first) worked out from the last four weeks of orders, counter sales included. A store with no orders yet sends an empty list and the row doesn't show — nothing is guessed. Tapping one opens that item's own sheet, so sizes and extras are still asked for; the sheet is rendered by `Storefront` for every screen.
- **Moving between screens keeps the scroll right** (19 Nov, user report): the menu, the order and More info share one page, so the window used to keep its scroll from one to the next, and a phone that had scrolled down the menu opened the order halfway down, at the form, with what was picked out of sight. `Storefront`'s `go()` notes the menu's scroll before leaving it; the order and More info open at the top, and coming back to the menu (Back, "Add more") returns to where it was. Change screens with `go()`, never `setScreen` directly (only the hand-off to the payment page does).
- **The phone's Back button** (19 Nov, user request): the order, More info and an item's sheet are each a step in the browser's history (`history.state.brixx`, a `Step`: the screen and whether a sheet is open; `stepOf` reads it, anything else is the menu). Back from the order or More info comes to the menu at the same place, Back on a sheet closes it, and Back from the menu leaves the store as before; it used to leave the store from the order, back to wherever the link was tapped. `go()`, `openSheet()` and `closeSheet()` add and take the steps, so the store's own back arrows, "Add more" and adding from a sheet go back through history too. `history.scrollRestoration` is `manual` while the store is open, as the page keeps the menu's place itself. Next's patched `pushState` keeps its own router state alongside ours.
- **Pay says what's missing** (19 Nov, user request): the button is greyed out only when nothing can be done (sending, closed, empty order). Otherwise a tap with something missing (`missing()` in `OrderScreen`, top to bottom: a marked line, the delivery area, the address, the name, the phone number, a way to pay) scrolls to it, puts the cursor in it, outlines it red and says what it needs under it; the message goes as soon as anything it's about changes. It used to grey out without a word, and on a phone the form is mostly off screen.
- **Fields are 16px** (`field`, the note): an iPhone zooms the page into any field smaller than that when it's tapped, and often stays zoomed.
- **Opening fast** (19 Nov, user request): `app/[slug]/loading.tsx` shows the store's outline in neutral greys (band, facts, pills, menu rows) the moment the link opens, instead of a blank page while the store is read; the status page has its own (`o/[token]/loading.tsx`). The server runs in Frankfurt (`vercel.json`, `fra1`) beside the API and database; in Washington, every visit crossed the Atlantic twice (measured 19 Nov: about 0.8 s once the API was awake, 69 s when Render's free plan had put it to sleep). The menu is still read fresh on every visit, so sold-out items and the dashboard's preview stay exact.
- **What the browser keeps** (`lib/cart.ts`, tested in `lib/cart.test.ts`): the cart per store (`brixx-cart-<slug>`) with when it last changed, brought back for a day (`CART_KEEPS_MS`) and let go after that (19 Nov, user request: last week's basket used to greet people); and the customer's name and number (`brixx-customer`, one for every store), saved only once an order has gone through and filled in on the next one, with "Not you? Clear them" for a shared phone.
- **When the store is closed** (16 Sep, user request), the API says so (`open`, with `opensWords`), and the page says it three times over: the badge reads "Closed · opens today at 5:00 pm", a note above the menu explains the menu can be looked at but not ordered from, and both Checkout buttons are disabled and read "Closed right now" with the opening time under them. Item cards were already dead while closed (`canOrder`). The server refuses a closed-store order anyway, so a page left open past closing time shows its message rather than taking the order.
- **The look** (16 Sep, user request, following the Bolt Food pages the user shared): **flat, not cards**. One surface (`bg-page`) throughout, hairlines (`border-border`) between things, and no boxed panels — on the menu, in the cart, at checkout and in the sheets. `bg-tile` is left for a photo's own square and a placeholder.
  - **The store's head** is the cover picture full width (224–320 px), the name centred over it with the logo above, "More info ›" beneath, and round Share and light/dark buttons floating top right. Under it, a row of three facts divided by hairlines: open or closed, pickup or delivery from its cheapest fee, and how they can pay.
  - **The item drawer** matches: a **× at the top right and Escape to close it** (16 Sep, user report: a drawer that filled the screen had no way out), the photo edge to edge at the top, the name large, sizes as pills, and extras as plain rows divided by hairlines with the price on the right — no boxed options. Its foot holds the stepper and "Add to order" on one line.
  - **Every item** is a flat row: name, two lines of description, the price, then the photo on the right with a round **+** tucked into its corner. A hairline divides one from the next; the category heading above them is big and bold.
  - **On a laptop** the same page becomes three columns inside `max-w-6xl`: the categories standing in a column on the left (the pinned strip is phone-only), the menu in the middle, and the order on the right behind a hairline, both sticky. The cart and checkout screens widen to `max-w-2xl`.
  - **The basket** floats over the menu on a phone as a rounded pill — basket, total, count — rather than a full-width bar.
  - **Pickup or delivery** sits in its own band under the facts, where it can't be missed (16 Sep, user report: it wasn't there). A store with no delivery zones says "Pickup only" instead.
  - **More info** is its own screen (`InfoScreen`, built to the user's reference, 16 Sep), reached from the cover or the area under the facts: the name, a line about allergies, then rows with an icon each — open now with today's times, Call us (a `tel:` link), Where we are (Google Maps) — a Get directions button, the pickup/delivery choice with each zone's fee, how to pay, and the week's hours with today in bold. The API sends `week` (the days) and `today` (the weekday where the store is) for it. There's no map picture: that needs a Google key, so the address opens the customer's own map app instead.
- **A sheet holds the page still** behind it (`useLockScroll` in `lib/lock-scroll.ts`, 16 Sep, user request): the item drawer used to let the menu scroll underneath. The page is fixed where it stands, not just `overflow: hidden`, which an iPhone ignores, and it goes back to the same place when the sheet closes; on a laptop the vanished scrollbar's width is padded so nothing shifts sideways. Use it in any new sheet or dialog.
- **The category pills** stay pinned at the top of the menu and follow the customer: `useMenuNav` (`lib/menu-nav.ts`, 16 Sep, user request) lights the section that has passed under the bar as they scroll, slides that pill along the strip into view, and holds the pill they tapped lit until the page arrives, so the pills don't flicker through every category on the way. The reading line is each section's own `scroll-margin-top`, so where a tap lands and where scrolling decides the pill can't drift apart on either layout, and keeps still where the phone asks for reduced motion. **Reading back up the menu is not the same rule in reverse**: the category above lights only once it is a third of the way down the screen, not the moment the heading below it slips under the bar and its last item peeps in — which is what the user saw on 16 Sep. The decision is a pure function, `nextLit`, with the cases in `lib/menu-nav.test.ts` (`pnpm --filter @brixx/storefront test`, the app's first tests).
- **The cart** is kept in the browser (`lib/cart.ts`) and priced with `priceOrder` from `@brixx/shared` for showing; the server prices the order itself. Lines that sold out or changed since they were added must come off before checkout.
- **Checkout** keeps one `orderId` per visit, so a retry records the order once. Paying online: the page's address is swapped for the order's status page, then the customer goes to Moolre's page, so Back lands on the status page.
- `app/[slug]/o/[token]/` is the order's status page. It asks Moolre at once when the customer comes back from paying, then looks again every 15 s while the order is open. "Pay" opens a fresh payment page when the last one lapsed.
- **Photos** come from Cloudflare R2's public address (the API gives full URLs: `photoUrl` on items, `coverUrl` and `logoUrl` on the store). They're plain `<img>` tags: the dashboard already made them small, so Next's image optimiser isn't needed. Without a photo a card shows the item's initials; without a cover the header band is the store's colour, and without a logo the store's initials show.
- **The store's heading** differs by screen (22 Oct, user request). On a phone, `StoreHero` is the cover across the top with the name over it and `StoreFacts` under it. On a laptop, a full-width cover stretched too far, and a coloured band with the photo framed in it looked cut off from the page, so `StoreHead` stands on the page itself: a small cover with the logo on its corner, the name, area and More info beside it, and the facts in a row under the name, closed by a hairline like every other section.
- **Ordering by chat** (`app/[slug]/chat`, `lib/chat.ts`, the `chat` action; a test, 21 Oct) is **switched off** (22 Oct, user decision): its page is not found and the action refuses unless `STOREFRONT_CHAT=on`. To try it on the laptop, set that and `OPENAI_API_KEY` in `apps/storefront/.env.local`. Only the storefront's server talks to OpenAI.

## Running

- `pnpm --filter @brixx/storefront dev` serves http://localhost:3001. To use an API on the laptop, set `BRIXX_API_URL=http://localhost:3000` in `apps/storefront/.env.local`. After changing `@brixx/shared` or the API client, build them first.
- **Deployed on Vercel** (13 Sep; this address since 1 Nov) at `https://brixxstorefront.vercel.app`, built from `main` by Vercel's GitHub link (each build shows as a GitHub deployment; a build's own long address needs a Vercel login, the short one is public). `STOREFRONT_URL` on Render must be this address, so the dashboard shows the right store link and QR code. `BRIXX_API_URL` isn't set there, so it uses the Render API. Until `brixx.com` is set up, store links are `<that address>/<slug>`.
